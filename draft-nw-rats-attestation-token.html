Arm's Normal World Platform Attestation Token

Abstract

Arm Normal World Attestation Evidence describe the Claims that will be included as part of the Attestation token, generated by Client running in Normal World of an underlying Arm platform.¶

This document describes the claims that are included as part of Platform attestation token generated from Normal World.¶

This informational document is published as an independent submission to improve interoperability with Arm's architecture. It is not a standard nor a product of the IETF.¶

1. Introduction

A Client in Normal World host running on an Arm platform can request an attestation token from the underlying platform.¶

As outlined in the RATS Architecture [RFC9334], an Attester produces a signed collection of Claims that constitutes Evidence about its target environment. This document focuses on the output provided by requests from the Normal World host for an attestation token that covers the state of Arm Platform. This output corresponds to Evidence in [RFC9334] and, as a design decision, Arm Platform attestation token is a profile of the Entity Attestation Token (EAT) [EAT]. Note that there are other profiles of EAT available, such as [I-D.kdyxy-rats-tdx-eat-profile] and [I-D.mandyam-rats-qwestoken], for use with different use cases and by different attestation technologies.¶

The platform token can be combined with the specific claims or individual tokens from the Secure World. The Secure World claims or token profiles are currently outside the scope of this specification.¶

This document focuses on exact syntax and semantics of the attestation claims, and defining the way these claims are encoded and cryptographically protected.¶

As mentioned in the abstract, this memo documents a vendor extension to the RATS architecture, and is not a standard.¶

2. Arm Normal World Platform Claims

The set of claims for the Arm Normal World Platform token are as follows:¶

arm-platform-claims = (arm-platform-claim-map)

arm-platform-claim-map = {
    arm-platform-profile
    arm-platform-challenge
    arm-platform-implementation-id
    arm-platform-instance-id
    arm-platform-config
    arm-platform-lifecycle
    arm-platform-sw-components
    ? arm-platform-verification-service
    arm-platform-hash-algo-id
    arm-platform-client-id
    ? arm-platform-manufacturing-config
    ? arm-platform-tbb-rotpk
}
¶

2.1. Caller Claims

2.1.1. Platform Challenge

This claim is used to carry a challenge provided by the relying party to demonstrate freshness of the generated token.¶

This claim MUST be present in the Normal World Platform attestation token.¶

The [EAT] eat_nonce (claim key 10) is used. Since the EAT nonce claim offers flexiblity for different attestation technologies, this specifications applies the following constraints to the nonce-type:¶

  • The length MUST be either 32, 48, or 64 bytes.¶

  • Only a single nonce value is conveyed. The array notation MUST NOT be used for encoding the nonce value.¶

arm-platform-challenge-label = 10

arm-platform-challenge = (
    arm-platform-challenge-label => arm-platform-hash-type
)
¶

2.2. Target Identification Claims

These claims establishes the identity of the Arm platform.¶

2.2.1. Arm Platform Implementation ID

The Implementation ID claim uniquely identifies the implementation of the Arm Platform. The value of the Arm platform Implementation ID claim can be used by a verification service to locate the details of the Arm platform implementation from an endorser or manufacturer. Such details are used by a verification service to determine the security properties or certification status of the Arm Platform implementation.¶

The value and format of the ID is decided by the manufacturer or a particular certification scheme. For example, the ID could take the form of a product serial number, database ID, or other appropriate identifier.¶

This claim MUST be present in an Arm Platform attestation token.¶

Note that this identifies the Arm Platform implementation, not a particular instance of the platform. To uniquely identify an instance, see the Instance ID claim Section 2.2.2.¶

arm-platform-implementation-id-label = 2396 ; Arm Platform implementation ID
arm-platform-implementation-id-type = bytes .size 32

arm-platform-implementation-id = (
    arm-platform-implementation-id-label =>
        arm-platform-implementation-id-type
)
¶

2.2.2. Arm Platform Instance ID

The Instance ID claim is a unique identifier of the Arm Platform instance. It can be used by a verifier to help locate an endorsement for the Attestation Key (PAK).¶

The EAT ueid (claim key 256) of type RAND is used. The following constraints apply to the ueid-type:¶

  • The length MUST be 33 bytes.¶

  • The first byte MUST be 0x01 (RAND) followed by the 32-byte unique identifier.¶

eat-ueid-rand-type = bytes .join eat-ueid-rand-fmt

eat-ueid-rand-fmt = [
  ; the type byte is 0x01
  ueid-rand-typ
  bytes .size 32
]

ueid-rand-typ = h'01'
¶

This claim MUST be present in an Arm Platform attestation token.¶

arm-platform-instance-id-label = 256 ; EAT ueid

arm-platform-instance-id-type = eat-ueid-rand-type

arm-platform-instance-id = (
    arm-platform-instance-id-label => arm-platform-instance-id-type
)
¶

2.3. Target State Claims

2.3.1. Normal World Arm Platform Profile Definition

The Normal World Arm platform profile claim identifies the EAT profile to which the Arm platform token conforms. This allows a receiver to assign the intended semantics to the rest of the claims found in the token.¶

The EAT eat_profile (claim key 265) is used.¶

The format of the Arm platform profile claim is defined as a text string of value "tag:arm.com,2026:cca_platform#2.0.0".¶

This claim MUST be present in an Arm Platform attestation token.¶

arm-platform-profile-label = 265 ; EAT profile

; To do check, if 1.0.0 is more appropriate here ?
arm-platform-profile-type = "tag:arm.com,2026:arm_nw_platform#1.0.0"

arm-platform-profile = (
    arm-platform-profile-label => arm-platform-profile-type
)
¶

2.3.2. Security Lifecycle

The Security Lifecycle claim represents the current lifecycle state of the Arm Platform.¶

The state is represented by an integer that is divided as follows:¶

  • major[15:8] - Arm Platform security lifecycle state, and¶

  • minor[7:0] - IMPLEMENTATION DEFINED state.¶

A non debugged Arm platform will be in arm-platform-lifecycle-secured state.¶

This claim MUST be present in a CCA Platform attestation token.¶

2.3.3. Platform Config

The Arm platform config claim describes the set of chosen implementation options of the Arm platform. As an example, these may include a description of the level of physical memory protection which is provided.¶

The Arm platform config byte string contains implementation information that is provided by the chip vendor and the device vendor. TODO Add the System level properties applicable here, when clear identified.¶

The layout and encoding of this information is IMPLEMENTATION DEFINED.¶

An attestation verifier should use information from the an attestation profile document applicable to the implementation to understand the IMPLEMENTATION DEFINED choices made for this field. Reference values can be accompanied by a bitmask identifying the relevant portion of the platform config claim.¶

This claim MUST be present in a Arm Platform attestation token.¶

arm-platform-config-label = 2401 ; Arm platform config
                                 ; TBD: add to IANA registration
arm-platform-config-type = bytes

arm-platform-config = (
    arm-platform-config-label => arm-platform-config-type
)
¶

2.3.4. Platform Manufacturing Config

The Arm platform manufacturing config claim represents a record of production phases and testing conducted during the manufacturing process for this instance.¶

The Arm platform manufacturing config claim is OPTIONAL in an Arm platform token¶

arm-platform-manufacturing-config-label = 2403

arm-platform-manufacturing-config-type = bytes

arm-platform-manufacturing-config = (
    arm-platform-manufacturing-config-label =>
        arm-platform-manufacturing-config-type
)
¶

2.3.5. Arm Platform Client ID

The Arm platform client ID claim identifies the security domain from which the attestation token was requested.¶

In this profile, it is the Normal World Caller ID value (value=X), set in this claim.¶

The Arm platform client ID claim MUST be present in a CCA platform token.¶

arm-platform-client-id-label = 2394 ; Arm platform namespace

arm-platform-client-id-nw = 3 ; TO DO check the correct value for NW Client

arm-platform-client-id-type =
    arm-platform-client-id-rmsd

arm-platform-client-id = (
    arm-platform-client-id-label => arm-platform-client-id-type
)
¶

2.3.6. Arm Platform TBB ROTPK

Where an implementation of the Arm platform follows the Trusted Board Boot specification [TBB], the platform will include several provisioned public key identifiers which are used to establish a chain of trust. The Arm platform TBB ROTPK claim is used to provide this information to a verifier.¶

The Arm platform tbb rotpk claim is OPTIONAL in a Normal World Arm platform token¶

arm-platform-tbb-rotpk-label = 2405

arm-platform-tbb-rotpk-type = [ + arm-platform-tbb-rotpk-item ]

arm-platform-tbb-rotpk-item = {
    1 => tstr,                     ; provisioning stage, e.g. "CM" or "DM"
    2 => int,                      ; index in the active array
    3 => arm-platform-hash-type    ; key digest
}

arm-platform-tbb-rotpk = (
    arm-platform-tbb-rotpk-label => arm-platform-tbb-rotpk-type
)
¶

2.4. Software Inventory Claims

2.4.1. Software Components

The Software Components claim is a list of software components which can affect the behavior of the Arm platform.¶

This claim MUST be present in a Arm Platform attestation token.¶

Each entry in the Software Components list describes one software component using the attributes described in the following subsections. Unless explicitly stated, the presence of an attribute is OPTIONAL.¶

It is expected that an implementation will describe the expected software component values within the profile. In some implementations, a software component may consist of a configuration data item.¶

Note that, as described in [RFC9334], a relying party will typically see the result of the appraisal process from the Verifier in form of an Attestation Result, rather than the Arm Platform token from the attesting endpoint. Therefore, a relying party is not expected to understand the Software Components claim. Instead, it is for the Verifier to check this claim against the available Reference Values and provide an answer in form of an "high level" Attestation Result, which may or may not include the original Software Components claim.¶

arm-platform-sw-components-label = 2399 ; PSA software components

arm-platform-sw-component = {
  ? 1 => text,                   ; component type
    2 => arm-platform-hash-type, ; measurement value
  ? 4 => text,                   ; version
    5 => arm-platform-hash-type, ; signer id
  ? 6 => text,                   ; hash algorithm identifier
  ? 7 => bool,                   ; live firmware activation supported
  ? 8 => [ + arm-platform-hash-type ],    ; list of countersigner ids
}

arm-platform-sw-components = (
    arm-platform-sw-components-label => [ + arm-platform-sw-component ]
)
¶
2.4.1.1. Component Type

The Component Type attribute (key=1) is a short string representing the role of this software component. This attribute is intended for use as a hint to help the verifier understand how to evaluate the CCA platform software component measurement value.¶

This attribute is optional in an Arm Platform software component.¶

2.4.1.2. Measurement Value

The Measurement Value attribute (key=2) represents a hash of the state of the software component in memory at the time it was initialized. The measurement values are implemented such that the values can only be extended rather than set. The values are initialised to 0, so the value reported in attestation will be H( 0 || H(software component)). TODO Check if LFA is supported on this profile and then update?¶

The value MUST be a cryptographic hash of 256 bits or stronger.¶

This attribute MUST be present in an Arm Platform software component.¶

2.4.1.3. Version

The Version attribute (key=4) is the issued software version in the form of a text string. The meaning of this string is defined by the software component vendor.¶

This attribute is optional in an Arm Platform software component.¶

2.4.1.4. Signer ID

The Signer ID attribute (key=5) uniquely identifies the signer of the software component. The identification is typically accomplished by hashing the signer's public key. The value of this attribute will correspond to the entry in the original manifest for the component. This can be used by a Verifier to ensure the components were signed by an expected trusted source.¶

This attribute MUST be present in an Arm Platform software component.¶

2.4.1.5. Measurement Description

The Measurement Description attribute (key=6) contains a string identifying the hash algorithm used to compute the corresponding Measurement Value. The string SHOULD be encoded according to "Hash Name String" in the "Named Information Hash Algorithm Registry" [IANA.named-information].¶
